# Harbor Registry Lab Design

Date: 2026-07-05

## Goal

Add Harbor as the lab container registry, then connect GitLab CI for the existing `ci-cd` WordPress folder so CI builds a Docker image and pushes it to Harbor.

This phase proves:

```text
GitLab CI -> Docker build -> Harbor push -> image visible in Harbor UI
```

## Scope

In scope:

- Install Harbor using Docker Compose.
- Use Harbor over plain HTTP for local lab use.
- Create Harbor project `vinfast`.
- Create Harbor robot account for CI push/pull.
- Configure GitLab CI to build and push the `ci-cd` image.
- Write detailed docs under `docs/harbor/README.md`.

Out of scope for this phase:

- ArgoCD deployment.
- k3d cluster.
- Harbor built-in Trivy scanner adapter.
- Production TLS certificates.
- External DNS/domain.
- Image promotion, retention, replication, signing, or Notary.

## Constraints

- Host has about 8GB RAM and 4 CPU.
- Build one component at a time.
- GitLab already runs at `http://localhost:8929`.
- Dependency-Track already runs at `http://localhost:8081` UI and `http://localhost:8080` API.
- DefectDojo already runs at `http://localhost:8082`.
- Documentation must be written under `docs/`.
- Harbor UI/registry endpoint: `http://localhost:8083`.
- Harbor project: `vinfast`.
- Harbor image name: `wordpress`.
- CI target is existing `ci-cd` WordPress folder.
- Harbor uses HTTP/insecure registry for lab convenience.
- Do not require all lab stacks to run simultaneously on the 8GB host.

## Recommended Approach

Use the official Harbor installer workflow because Harbor requires generated configuration, internal secrets, registry token certificates, nginx routing, and multiple service-specific config files. Treat the official installer output as the source of truth rather than hand-writing a fragile Harbor compose file from memory.

Repository layout:

```text
infra/harbor/
  harbor.yml
  common/                # generated by Harbor prepare/install process
  docker-compose.yml     # generated by Harbor prepare/install process

docs/harbor/README.md
```

Harbor is still run by Docker Compose, but the compose file is generated by the official Harbor installer from `harbor.yml`.

Required Harbor services generated by the installer:

- `log`
- `registry`
- `registryctl`
- `postgresql`
- `core`
- `portal`
- `jobservice`
- `redis`
- `proxy`

Harbor Trivy adapter is not enabled in this phase because Trivy and Dependency-Check are already covered by the GitLab CI + DefectDojo flow.

## Harbor Configuration

Create `infra/harbor/harbor.yml` from Harbor's template with lab values:

- `hostname: host.docker.internal` so Harbor token realm is reachable from GitLab DinD and k3d clients
- `http.port: 8083`
- no external HTTPS section
- `harbor_admin_password`: stable lab password
- `database.password`: stable lab password
- data volume under `./data`
- `trivy.ignore_unfixed`: keep default if the section exists, but scanner service is not required for this phase

The docs must explain that Harbor runs as an insecure HTTP registry. Docker Desktop must trust `localhost:8083` and `host.docker.internal:8083`, and GitLab Runner's Docker-in-Docker service must start with `--insecure-registry=host.docker.internal:8083` or equivalent.

## Data Flow

1. User installs/starts Harbor using the documented Docker Compose/installer steps.
2. User opens Harbor UI at `http://localhost:8083`.
3. User logs in as `admin` with the configured lab password.
4. User creates Harbor project `vinfast`.
5. User creates robot account with push/pull permissions for project `vinfast`.
6. User stores robot credentials in GitLab CI variables.
7. GitLab CI builds the WordPress image from `ci-cd/Dockerfile`.
8. GitLab CI tags the image:
   - `${HARBOR_URL}/${HARBOR_PROJECT}/${HARBOR_IMAGE_NAME}:${CI_COMMIT_SHORT_SHA}`
   - `${HARBOR_URL}/${HARBOR_PROJECT}/${HARBOR_IMAGE_NAME}:latest`
9. GitLab CI logs in to Harbor with robot credentials.
10. GitLab CI pushes both tags.
11. User verifies image repository and tags in Harbor UI.

## GitLab CI Integration

Modify `ci-cd/.gitlab-ci.yml`:

- Add stage order:

```yaml
stages:
  - build
  - security
```

- Add job `harbor-build-push` in `build` stage.
- Preserve existing Dependency-Track and DefectDojo security jobs.
- Use Docker-in-Docker because runner already uses Docker executor.
- Configure DinD for insecure registry.

Required GitLab CI variables:

- `HARBOR_URL` — `host.docker.internal:8083` for Docker Desktop runner containers.
- `HARBOR_PROJECT` — `vinfast`.
- `HARBOR_IMAGE_NAME` — `wordpress`.
- `HARBOR_ROBOT_USER` — robot account username from Harbor.
- `HARBOR_ROBOT_TOKEN` — robot account token from Harbor.

Build job behavior:

- `docker login` to Harbor.
- `docker build` from `ci-cd` project root.
- tag commit SHA and `latest`.
- push both tags.
- fail if login/build/push fails.

## Documentation Requirements

Create `docs/harbor/README.md` with careful, step-by-step instructions:

1. Prerequisites and resource warning.
2. Stop optional heavy stacks if memory is tight.
3. Download/prepare Harbor installer or use checked-in `infra/harbor` files if already present.
4. Configure `infra/harbor/harbor.yml`.
5. Start Harbor.
6. Verify containers.
7. Open UI at `http://localhost:8083`.
8. Login as `admin`.
9. Create project `vinfast`.
10. Create robot account with push/pull permissions.
11. Configure Docker Desktop insecure registry for `localhost:8083`.
12. Configure GitLab CI variables.
13. Run pipeline.
14. Verify pushed image/tags in Harbor UI.
15. Stop Harbor without deleting data.
16. Delete Harbor data.
17. Troubleshoot:
    - port conflict
    - insecure registry error
    - robot login failure
    - DinD cannot reach Harbor
    - push denied
    - low memory

## Files to Create or Modify

- Create `infra/harbor/harbor.yml` or document generation from official template.
- Create `docs/harbor/README.md`.
- Modify `ci-cd/.gitlab-ci.yml` to add `harbor-build-push` while preserving existing security jobs.
- Optionally create helper scripts under `scripts/harbor-*` only if they reduce copy/paste mistakes.

## Success Criteria

- Harbor starts successfully through Docker Compose.
- Harbor UI reachable at `http://localhost:8083`.
- Admin login works.
- Project `vinfast` exists.
- Robot account for CI exists and has push/pull permission.
- Docker can login to `localhost:8083` after insecure registry config.
- GitLab CI build job builds the WordPress image from `ci-cd/Dockerfile`.
- GitLab CI pushes commit-SHA and `latest` tags to Harbor.
- Harbor UI shows repository `vinfast/wordpress` with both tags.
- `docs/harbor/README.md` documents all setup, usage, verification, and cleanup steps.

## Resource Strategy

Because host has about 8GB RAM:

- Harbor is installed as an independent phase.
- Do not require GitLab, Dependency-Track, DefectDojo, Harbor, and k3d to run together.
- For Harbor UI setup, GitLab can be stopped if not needed.
- For CI push testing, GitLab + Harbor must run; Dependency-Track and DefectDojo can be stopped if RAM is tight.
- ArgoCD/k3d phase starts after Harbor push works.

## Risks and Mitigations

- Harbor official installer generates files that can drift if edited manually.
  - Mitigation: docs clearly separate editable `harbor.yml` from generated files.
- Insecure registry config differs between host Docker, GitLab DinD, and later k3d.
  - Mitigation: docs include each surface separately.
- Robot token is sensitive.
  - Mitigation: store only in GitLab masked CI variables, never commit.
- Harbor is heavier than Dependency-Track and DefectDojo.
  - Mitigation: start only required stacks during tests.
